# The app reads preferences through a public `config --json` query

Status: accepted (2026-10-25, maintainer)

The app may run exactly two fixed core invocations: the scan, `versionbar list --json`, and the preferences query, `versionbar config --json`. Both use fixed arguments through the same bundled-uv launch as the scan (ADR 0006, ticket 21); Rust never passes other arguments and never parses TOML. The query prints a `ConfigResult` (generated, like every output model): the resolved config file path, whether it exists, any problems, and the preferences the app needs (`update_check`, `pinned`, `order`). It exits 0 when the config is usable and 3 when it is not, still printing the path and the problems so the app can open the file for fixing, with `preferences` null; an unknown update preference never means "enabled". On an invalid config the scan invocation fails too: `list --json` exits 3 with empty stdout and the problems on stderr, which the app reports as a failed scan (ticket 21 already maps a nonzero exit to failed/exit with stderr); it may then run `config --json` to find the file and its problems. The command is public rather than hidden because people need the same answer ("where is my config, and what does it set?") and because the app's dependence makes it a stable contract either way. Considered: a hidden `debug`-style command (rejected: the contract would be just as fixed while invisible to users), putting preferences into the scan result (rejected: it mixes settings into inventory and makes the app scan to learn whether it may check for updates), and Rust reading the file itself (rejected: hard rules forbid TOML parsing and duplicated config logic in Rust).
